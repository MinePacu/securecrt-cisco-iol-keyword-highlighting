# 4차 진단: --- 규칙 순서만 변경

후속 결과: 사용자 제공 화면에서 ICMP 네 열과 정적 NAT 두 주소가 모두 의도한 색상으로
표시되었습니다. 아래 가설은 이 사례에서 순서 변경에 따른 표시 차이로 뒷받침됐으며,
앱 내부 처리 방식 자체를 확인한 것은 아닙니다. 다른 출력의 오탐 제한은 그대로 남습니다.

## 관찰과 가설

3차 사용자 화면에서 Position의 주소 강조는 실패했고 Suffix의 ICMP 네 열은 성공했습니다.
Suffix에서도 정적 NAT의 두 주소는 기본색이었습니다. 두 행의 주요 차이는 뒤쪽 필드가
주소인지 `---`인지입니다. 기존 목록은 `---`를 주소 규칙보다 먼저 강조합니다.

**가설:** 우선 규칙으로 강조된 `---` 구간 때문에 후순위 주소 규칙이 뒤쪽 문맥을
검사하지 못할 수 있습니다. 이는 아직 확인되지 않은 가설이며 SecureCRT 내부 동작의
확정 설명이 아닙니다. 문법이나 패턴을 동시에 바꾸지 않고 순서만 바꿉니다.

## 적용

1. NAT-Probe4-DashLast.ini를 Keywords에 복사합니다.
2. 현재 세션에서 NAT-Probe4-DashLast를 선택합니다. 색상 강조와 구문/부분 문자열 매칭을 유지합니다.
3. 기존 `do sh ip nat t`를 실행해 ICMP와 정적 NAT가 함께 있는 새 출력 화면을 보내 주세요.

이 파일은 NAT-Probe3-Suffix와 규칙/색상이 같고 `---` 규칙 하나만 맨 뒤로 이동했습니다.
Pro=빨강, icmp=분홍, 네 열=골드/시안/하늘색/보라, ---=은색입니다.
정적 NAT의 `211.239.123.254`가 골드, `10.1.1.1`이 시안으로 바뀌는지가 핵심입니다.

- ICMP를 유지하면서 정적 주소도 성공: 이 사례에서 규칙 순서 영향이 입증됨.
- 정적 주소만 계속 실패: 이 변경으로 해결되지 않음. 다음에는 --- 전용 suffix를 별도 분리.
- ICMP까지 달라짐: 선택된 목록과 새 출력 여부부터 확인.

## 오탐 검사 결과와 운영 제한

`NatProbe4.Tests.ps1`은 순서만 바뀌었는지 검증하고 suffix 방식의 오탐을 재현합니다.
예: gateway 설명과 ACL의 마지막 IP, 일반 연결 설명의 IP:port가 Outside global 색으로
분류됩니다. 필드가 빠진 NAT 행은 남은 개수에 따라 잘못된 열색을 받을 수 있습니다.
이는 .NET 정규식 수준에서 재현한 결과이며 운영 목록에서의 실제 색상은 우선순위에
따라 달라질 수 있습니다.

따라서 이 목록은 진단용입니다. 오탐 방지가 해결됐다고 주장하거나 운영 V3에 합치지
않습니다. 뒤쪽 문자열만으로 NAT인지 구별할 수 없는 경우가 있어, 운영 반영에는
추가 문맥 조건 또는 NAT 전용 목록을 별도 선택하는 방식이 필요합니다.
포트를 필수로 만드는 것만으로는 일반 연결 설명의 오탐을 막을 수 없으며 정적 NAT도 제외됩니다.

실제 화면 결과 확인 전에는 매칭 방식이 완성됐다고 판단하지 않습니다.
